# Deploying TestByte (free tier)

This stack is free to run today and deliberately avoids vendor lock-in: a standard Docker image for the
backend and plain Postgres, so moving to Azure later (see the bottom of this doc) is a config change, not
a rewrite.

## 1. Database — Neon (free Postgres)

1. Create a free account at [neon.tech](https://neon.tech) (no credit card required).
2. Create a new project. Note the connection details it gives you — you need the host, database name,
   username, and password.
3. Neon requires SSL. Your `DB_URL` will look like:
   ```
   jdbc:postgresql://<your-neon-host>/<db-name>?sslmode=require
   ```
4. Create a database user/database if Neon didn't already (it usually provisions one `neondb` database
   and a default role for you — that's fine to use directly).

## 2. Zoho SMTP app password

1. Log into Zoho Mail as `ravitejananduri@zoho.com`.
2. Go to **Settings → Security → App Passwords**.
3. Generate a new app password for "TestByte backend". Copy it — this is your `MAIL_PASSWORD`
   (not your regular Zoho login password).

## 3. Backend — Render (free web service)

1. Create a free account at [render.com](https://render.com) and connect your GitHub account.
2. **New → Blueprint**, pick the `TestByte` repo. Render will read `render.yaml` at the repo root and
   propose a `testbyte-backend` web service built from `backend/Dockerfile`.
3. When prompted, fill in the env vars marked "sync: false" in `render.yaml`:
   - `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` — from Neon (step 1)
   - `MAIL_USERNAME` — `ravitejananduri@zoho.com`
   - `MAIL_PASSWORD` — the Zoho app password (step 2)
   - `MAIL_FROM` — `ravitejananduri@zoho.com`
   - `FRONTEND_BASE_URL` — your Vercel URL once you have it (step 4) — you can come back and set this
     after deploying the frontend; it's used to build links inside emails.
   - `JWT_SECRET` is auto-generated by Render (`generateValue: true`) — no action needed.
4. Deploy. Render builds the Docker image and starts the service. First boot runs the Flyway migrations
   against Neon automatically.
5. Note the resulting URL, e.g. `https://testbyte-backend.onrender.com`.

**Free tier caveat:** Render's free web service spins down after ~15 minutes of inactivity. The first
request after idle takes ~30-50s (cold start) while it wakes back up. Fine for low-volume recruiting use;
upgrade to a paid instance later if this becomes annoying.

## 4. Frontend — Vercel (free)

1. Create a free account at [vercel.com](https://vercel.com) and connect GitHub.
2. **Add New → Project**, pick the `TestByte` repo, set **Root Directory** to `frontend`.
3. Before (or after) the first deploy, edit [frontend/src/environments/environment.ts](frontend/src/environments/environment.ts)
   and set `apiBaseUrl` to your Render backend URL from step 3, e.g.
   `https://testbyte-backend.onrender.com/api`. Commit and push — Vercel auto-deploys on push to `main`.
4. Vercel gives you a URL like `https://testbyte.vercel.app`. Go back to Render and set `FRONTEND_BASE_URL`
   to this value (used to build links in emails), then redeploy the backend service.

## 5. First run

1. Open your Vercel URL and sign up with your own email/password — **the very first account created
   becomes an approved admin automatically** (no approval needed for account #1).
2. Log in. You'll land on the pending-approvals screen. From here you can:
   - Change the approver notification email under **Settings** (defaults to
     `ravitejananduri@zoho.com`, seeded by the first Flyway migration).
   - Invite additional admins under **Invite admin**.
3. Any further signups go through the pending-approval flow and email the approver address above.
4. The 3 sample tests (Java/Python/SQL) are already seeded — recruiters can schedule them immediately
   from **Schedule test**.

## 6. CI

`.github/workflows/backend-ci.yml` and `frontend-ci.yml` run tests on every push/PR (Postgres service
container for the backend, `npm run build && npm test` for the frontend). They gate visibility only —
Render and Vercel deploy independently via their own GitHub integration on push to `main`. If you want CI
to be a hard gate, add a branch protection rule on `main` requiring both workflows to pass before merge.

---

## Moving to Azure later

Nothing here is Render/Vercel/Neon-specific at the application level, so the move is a redeploy, not a
rewrite:

- **Backend**: the same `backend/Dockerfile` image redeploys as-is to Azure App Service (Web App for
  Containers) or Azure Container Apps — just point it at a new registry/build pipeline and carry over the
  same env vars.
- **Database**: the backend only uses standard JDBC + Flyway against Postgres, no Neon-specific features.
  Migrating to Azure Database for PostgreSQL is a `pg_dump` from Neon, `pg_restore` into Azure, and a
  `DB_URL` change.
- **Frontend**: swap Vercel for Azure Static Web Apps — same Angular build output
  (`dist/frontend/browser`), just a different host serving it.
- **CI/CD**: GitHub Actions stays as-is. If the repo moves to a different GitHub org/business account,
  re-point any deploy-target secrets under that org's repo settings — the workflow YAML itself doesn't
  hardcode an org/account.
